# 交互协议（interaction-protocol）

驱动"生成 → 审核 → 迭代 → 定稿"的完整规则。**实测结论：三数字打分（内容/案例/图片 0-10 分）对懒人老师不友好，已废除，改为单个数字指令协议**。

## 数字审核协议（当前唯一协议）

每一节教案生成后，提示用户**用一个数字回复**（不用打字，懒人友好）：

```
1 = 继续下一节（本节能用，通过）
0 = 直接生成全部，不再逐节审核（整本模式）
W{周次} = 只抽查/重做指定周（如 W2 = 只审第 2 周；W5-8 = 审第 5-8 周；整本审核免去逐节过目，适合 18 周大教案）
2 = 图片重新生成
3 = 案例重新生成
4 = 内容重新生成
5 / 6 / 7 = 指定组合重新生成（首次交互时与用户约定组合含义，例如：
            5 = 内容+图片、6 = 内容+案例、7 = 案例+图片）
9 = 全部重新做
```

- 数字即指令，解析失败时重述格式并要求重发，不猜测。
- 用户回复"ok""好""可以""1"等自然词也按"继续下一节"处理。
- 对单节模式，"继续"＝该节定稿交付；对整本模式，"继续"＝进入下一节。

## 重生成处理

- **2 图片** → 回到配图引擎重新执行（补图/换图/重刷错字图），说明换/补了哪些图。
- **3 案例** → 回到案例引擎重新执行（重新检索真实案例 / 换案例 / 强化六要素细节），说明换了哪个案例、怎么改的。
- **4 内容** → 重写充实（补充细节、步骤、逻辑展开，尤其检查实施过程可操作性、时间预算是否填满课时）。
- **5/6/7 组合** → 按约定组合同时重做对应维度。
- **9 全部** → 该节全部重做。
- 每次重做后**说明改了什么**，再次请用户数字确认。
- 同一节最多自动迭代 3 轮；3 轮后仍不满意，询问用户具体修改要求，不无限循环。

## 确认与继续

- 用户回复 `1`（或 ok/好/可以）即通过：
  - 单节模式 → 该节定稿，输出 Word，任务结束。
  - 整本模式（默认逐节审核）→ 进入下一节，重复"生成 → 数字确认"。
- 用户回复 `0` → 整本模式切换为快速模式，一次输出剩余全部节、不再逐节确认；输出时提示"如需调整某节，可指定第几节修改"。
- 用户回复 `W{周次}`（如 W2、W5-8）→ 只对指定周次做抽查式生成/重做，其余周次暂不输出；抽查通过后可按 0 继续批量。

## 采集快车道（懒人一次打包）

- 默认一次一问；若用户主动表示"别问了，直接说"或一次性给出全部信息（课程名+学时+类型+平台+模板等），**直接按打包信息执行**，不再逐项追问；缺少的信息用"只有课程名兜底"补全（见 SKILL.md 第 1 节）。

## 整本模式流程

1. 开始前询问：逐节审核（默认）还是快速模式（一次出全部）？
2. **先做预研核实**（见 SKILL.md 3.1）：检索人才培养方案 → 出约 500 字教学目标与内容框架 → 用户核实（用户此时会看得很仔细）。核实通过后进入逐节/批量生成。
3. 逐节审核：每节生成 → 数字确认 → 通过后下一节；全部通过后组装整本并交付。
4. 快速模式：按已核实框架一次生成全部课时教案，交付整本；交付时提示可指定某节修改。
5. 整本交付后若用户指出某节问题（如某节图片没显示、内容漏填），按"第几节"定点重做，重新生成后必须重新验收（audit + 图片数量核对）。

## 记录

- 每节数字反馈记入生成过程；用户对某节的选择（继续/重做维度）在交付说明中可体现，供老师留档。
