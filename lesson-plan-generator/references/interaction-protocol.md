# 交互协议（interaction-protocol）

驱动"生成 → 审核 → 迭代 → 定稿"的完整规则。**实测教训：原"内容/案例/图片三数字打分"对懒人老师不友好，已废除；改为单数字指令协议。**

## 数字协议（唯一协议）

每一节生成后，提示用户**用一个数字回复**（不用打字，懒人友好）：

```
1 = 继续下一节（本节能用，通过）
0 = 直接生成全部，不再逐节审核（整本模式）
2 = 图片重新生成
3 = 案例重新生成
4 = 内容重新生成
5 / 6 / 7 = 指定组合重新生成（首次交互时与用户约定，如 5=内容+图片、6=内容+案例、7=案例+图片）
9 = 全部重新做
```

- 数字即指令；解析失败时重述格式并要求重发，不猜测。
- "ok / 好 / 可以 / 1"等自然确认同样视为"继续下一节"。
- 单节模式"继续"= 该节定稿；整本模式"继续"= 进入下一节。

## 重生成处理

- **2 图片** → 回到配图引擎重跑（补图/换图/重刷错字图），说明换了哪些图。
- **3 案例** → 回到案例引擎重跑（重检索真实案例/换案例/强化六要素细节），说明换了哪个案例、怎么改的。
- **4 内容** → 重写充实（补细节、步骤、逻辑展开；重点检查实施过程可操作性、时间预算是否填满）。
- **5/6/7 组合** → 按约定的维度同时重做。
- **9 全部** → 整节重做。
- 每次重做后**说明改了什么**，再次请用户数字确认。
- 同一节最多自动迭代 3 轮；3 轮后仍不满意，询问用户具体修改要求，不无限循环。

## 确认与继续

- 用户回复 `1`（或 ok/好/可以）＝通过：
  - 单节模式 → 该节定稿，输出 Word，任务结束。
  - 整本模式（默认逐节审核）→ 进入下一节，重复"生成 → 数字确认"。
- 用户回复 `0` → 整本模式切换快速模式：一次输出全部剩余课时，不再逐节确认；交付时提示"如需调整某节，可指定第几节修改"。

## 整本模式流程

1. 开始前询问：逐节审核（默认）还是快速模式（一次出全部）？
2. **先做预研核实**（见 SKILL.md 3.1）：检索人才培养方案 → 出约 500 字教学目标与内容框架 → 用户核实（用户会仔细看）。确认后再进入逐节/批量生成。
3. 逐节审核：生成一节 → 数字确认 → 通过后下一节；全部通过后组装整本并交付。
4. 快速模式：从已核实框架一次生成全部课时教案并交付；交付时提示"如需调整某节，可指定第几节修改"。
5. 整本交付后，若用户指出具体问题（如某节图片没显示、内容缺失），按节号重做该节；重做后重新验证（audit + 该节图片数）。

## 记录

- 每节数字反馈记入生成过程；交付时可附一页"教案评分总览"（各节通过/重做维度），供老师留档。
